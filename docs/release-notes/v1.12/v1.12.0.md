## Summary

v1.12 turns config templates and configs into Kubernetes resources reconciled by the controller,
and adds a set of composition features behind feature gates: SourceDefinition and CEL property
expressions, `forEach` workflow steps, module and addon components, and definition inheritance.
vela-core now manages its own admission webhook and cluster-gateway serving certificates.

Read these notes before upgrading from KubeVela 1.11 or earlier. Several changes listed here were
also backported to [v1.11.1](../v1.11/v1.11.1.md); each one says so.

## Breaking changes

### Trait conflicts

Admission now rejects an Application when an attached trait conflicts with
another trait through `TraitDefinition.spec.conflictsWith`.

KubeVela 1.11 accepted these Applications. Check existing Applications before
upgrading. An existing Application with conflicting traits is denied the next
time it is updated.

Also in v1.11.1 ([#7303](https://github.com/kubevela/kubevela/pull/7303)).

### Config templates and configs

Config templates and configs are now `ConfigTemplate` and `Config` resources. Users need
permissions on the new resources, `outputs` objects are created in the Config's namespace, and the
controller rather than the CLI publishes to Nacos. The full list of changes to check is in the
[upgrade guide](../../upgrade/v1.12/index.md#config-templates-and-configs).

## Behaviour changes

### Runtime certificates

vela-core now manages the serving certificates for admission webhooks and
cluster-gateway. At startup, it:

- creates or reuses the certificate Secrets (`<fullname>-admission` and
  `<fullname>-cluster-gateway-tls-v2`);
- sets the `caBundle` on webhook configurations and the cluster-gateway
  `APIService`;
- checks the certificates every minute and renews them when needed.

The old `kube-webhook-certgen` Jobs are no longer used. Existing Secrets from
those Jobs are reused during an upgrade, so the CA does not change.

This change prevents a deadlock with `helm install --wait` on Kubernetes 1.36.
Previously, vela-core could wait for the `APIService` while Helm waited to run
the Job that set its `caBundle`.

vela-core manages each certificate when these chart values are set:

- admission webhook: `admissionWebhooks.enabled=true`,
  `admissionWebhooks.patch.enabled=true`, and
  `admissionWebhooks.certManager.enabled=false`;
- cluster-gateway: `multicluster.enabled=true`,
  `multicluster.clusterGateway.secureTLS.enabled=true`, and
  `multicluster.clusterGateway.secureTLS.certManager.enabled=false`.

If `admissionWebhooks.patch.enabled=false` and
`admissionWebhooks.certManager.enabled=false`, provide the
`<fullname>-admission` Secret and the webhook `caBundle` yourself. Other
`admissionWebhooks.patch.*` settings only remain for compatibility with
existing values files.

Tools that render without cluster access, such as Argo CD, render the webhook
`failurePolicy` as `Ignore`. vela-core sets the configured policy at runtime.
Add `ignoreDifferences` entries in Argo CD so it does not report drift:

```yaml
ignoreDifferences:
  - group: admissionregistration.k8s.io
    kind: MutatingWebhookConfiguration
    jqPathExpressions:
      - .webhooks[].failurePolicy
  - group: admissionregistration.k8s.io
    kind: ValidatingWebhookConfiguration
    jqPathExpressions:
      - .webhooks[].failurePolicy
```

Also in v1.11.1 ([#7477](https://github.com/kubevela/kubevela/pull/7477), backported as
[#7478](https://github.com/kubevela/kubevela/pull/7478)).

### Definition namespace restrictions

The new `RestrictDefinitionNamespaces` feature gate is on by default. It enforces a definition's
`spec.restrictions`, or its `definition.oam.dev/restrict-namespaces` annotation, when an
Application is written. It does nothing until a definition declares a restriction.

## CRD changes

KubeVela 1.12 adds required CRDs (`configs.config.oam.dev`,
`configtemplates.config.oam.dev`, and `sourcedefinitions.core.oam.dev`) and
updates existing CRD schemas.

`vela install` updates CRDs automatically. `helm upgrade` never installs or
updates CRDs from a chart's `crds/` directory, so apply them before running
`helm upgrade`:

```shell
helm pull kubevela/vela-core --version <1.12-version> --untar
kubectl apply -f vela-core/crds/
```

The updated schemas are `applications`, `applicationrevisions`, `componentdefinitions`,
`definitionrevisions`, `policydefinitions`, `traitdefinitions`, `workflowstepdefinitions` and
`workflows`. They add the fields for definition restrictions and inheritance (`spec.extends`),
Application `sources`, and `forEach` workflow steps.

## Helm chart changes

### Built-in definitions

Helm no longer owns the built-in definitions directly. Hook Jobs now manage
them:

- A pre-upgrade Job adds `helm.sh/resource-policy=keep` to existing
  definitions. This keeps the definitions and their `DefinitionRevision`
  objects during the change in ownership.
- A post-install, post-upgrade, and post-rollback Job waits for the new
  controller, then applies the definitions with server-side apply.
- A pre-delete Job removes the definitions during `helm uninstall`.

The Jobs use these chart values:

| Value | Default | Purpose |
| ----- | ------- | ------- |
| `builtinDefinitions.job.image.repository` | `alpine/k8s` | Image that provides a shell and `kubectl` |
| `builtinDefinitions.job.image.tag` | `1.31.13` | Image tag |
| `builtinDefinitions.job.image.pullPolicy` | `IfNotPresent` | Image pull policy |
| `builtinDefinitions.job.rolloutTimeoutSeconds` | `300` | Controller rollout timeout; with cert-manager, also the webhook `caBundle` timeout |
| `builtinDefinitions.job.applyRetries` | `6` | Maximum definition apply attempts |

For an air-gapped cluster, mirror the Job image and set
`builtinDefinitions.job.image.repository`.

Also in v1.11.1 ([#7436](https://github.com/kubevela/kubevela/pull/7436)).

### Other values

- `featureGates.*` values for the new feature gates, including
  `featureGates.autoMigrateLegacyConfigs`.
- `workflow.httpDeny.*`, `featureGates.disableWorkflowHTTP` and
  `featureGates.blockPrivateHTTPAddresses` for the workflow HTTP guard (also in v1.11.1).

## CLI changes

- `vela config-template migrate` and `vela config migrate` adopt v1.11 templates and configs; see
  [Migrate Configs to ConfigTemplate and Config](../../upgrade/v1.12/config-migration.md).
- `vela def test` runs CUE tests for X-Definitions.
- `vela module` (`init`, `deploy`, `publish`, `registry`) manages modules.
- `vela config create` and `vela config-template apply` now create `Config` and `ConfigTemplate`
  resources.

Each command's flags are on its page under [vela CLI](../../cli/vela.md).

## New features

- **Config templates and configs as resources**: `ConfigTemplate` and `Config`, with template scope,
  cross-namespace access, sensitive rules and Nacos publishing from the controller; see
  [Config Template](../../reference/config-template.md).
- **SourceDefinition** and CEL `$( )` property expressions, including reading another component's
  output (`EnableCelExpressions`).
- **Workflow**: `forEach` steps with items from expressions and named by a key, CEL conditions on
  steps, expressions resolved when each step runs, and restarting before the first run.
- **Modules**: install a module as an Application component or inline with an addon, with
  identity stamping and hub and runtime placement (`EnableModuleComponent`).
- **Declarative addon component** (`EnableAddonComponent`).
- **Definitions**: inheritance and abstract definitions (`EnableDefinitionInheritance`), namespace
  restrictions, per-namespace usage quotas, and admission validation of WorkflowStepDefinition
  templates.
- **defkit**: Application-scoped and global policies, definition inheritance, reading a `forEach`
  pass from a step template, and expression-based validator messages.
- **Workflow steps**: configurable HTTP timeout on `request`, `webhook` and `notification`.
- **Traits**: `sidecar` supports `ports` (also in v1.11.1).

## Bug fixes

- Built-in definitions: fixes across components, traits and workflow steps so every documented
  parameter renders ([#7445](https://github.com/kubevela/kubevela/pull/7445)). A changed Pod
  template restarts Pods, so test affected Applications before upgrading. Parameters are in the
  [Reference](../../end-user/components/references.md) pages.
- `helmchart` releases install on the topology's clusters as the Application's user.
- Resource keeper honours shared-resource, GC-propagation and orphan-finalizer protections on
  delete (also in v1.11.1).
- PolicyDefinitions are validated with the compiler of their scope, and global and
  Application-scoped policy changes propagate (also in v1.11.1).
- Workflow HTTP is guarded against SSRF
  ([GHSA-8p2m-f3vg-8jwg](https://github.com/kubevela/kubevela/security/advisories/GHSA-8p2m-f3vg-8jwg),
  also in v1.11.1).
