## Summary

A security patch. Every image KubeVela ships or runs by default moves off the compromised eMudhra
CA chains, and fixes from the v1.12 release testing limit what an Application's HTTP requests,
`vela-cli` steps and credentials can reach. Everyone on v1.11 should upgrade. Some fixes change
behaviour, so read the breaking changes first.

## Breaking changes

- **`helm upgrade --reuse-values`.** With the values of v1.11.1 the chart fails to render, because
  the new `workflow.http` values are missing. Pass your own values file, or use
  `--reset-then-reuse-values` (Helm 3.14 and later). If your values set
  `multicluster.clusterGateway.image.tag` or `builtinDefinitions.job.image.tag`, update or remove
  them.
- **`vela-cli` step.** Its Job runs in the Application's namespace as the service account named in
  `serviceAccountName` (default `default`), instead of in `vela-system` as vela-core. The step fails
  if that account does not exist. Give the account the permissions the command needs
  ([#7592](https://github.com/kubevela/kubevela/pull/7592)).
- **HTTP request limits.** A workflow or definition HTTP request fails if it calls a loopback
  address, if its timeout is zero, negative, has no unit or is longer than
  `workflow.http.maxTimeout` (`60s`), or if the response is larger than
  `workflow.http.maxResponseBytes` (1 MiB). The `request` step fails on an HTTP 400
  ([#7592](https://github.com/kubevela/kubevela/pull/7592)).
- **Credentials and sources in other namespaces.** `helmchart` repository credentials and
  `valuesFrom` sources, configs read by config steps and Terraform module SSH keys are read only
  from the namespace that uses them. Move them there before you upgrade
  ([#7592](https://github.com/kubevela/kubevela/pull/7592)).
- **Webhooks with cert-manager.** With cert-manager, or a certificate you supply, the webhooks use
  `admissionWebhooks.failurePolicy` (`Fail`) from the first install.

## Behaviour changes

- Loopback, unspecified and local-use NAT64 addresses are always refused by the workflow HTTP
  guard, and `oci://` chart pulls go through the same check.
- CUE nested more than 1000 levels is refused before it is parsed.
- The query provider never returns a Secret's data. With `authentication.withUser=false`, a
  hand-written `app.oam.dev/username` is ignored. With
  `authorization.definitionValidationEnabled`, referenced Workflows and Policies are checked too.

`ghcr.io/osscontainertools/kaniko:v1.29.1` by digest.

## Bug fixes

- The vela-core and vela-cli images are built on `alpine:3.24`, pinned by digest
  ([#7644](https://github.com/kubevela/kubevela/pull/7644)).
- The `build-push-image` step defaults to `ghcr.io/osscontainertools/kaniko:v1.29.1` instead of
  `oamdev/kaniko-executor:v1.9.1`; a step that sets `kanikoExecutor` keeps its image
  ([#7633](https://github.com/kubevela/kubevela/pull/7633)).
- A `request` step succeeds on a reply that is not JSON; `responseBody` holds it.
- A definition revision that an Application pins (`type@vN`) is never garbage-collected.
- Completed `webhook` and `notification` steps no longer run again after a stale-cache conflict.
- A `helmchart` release owned by another Application is refused instead of being overwritten.
- `vela workflow rollback` continues at once instead of waiting for the next resync.
- Lists in updated objects are replaced exactly, owned children are listed in their own namespace,
  and `vela/http` request headers in templates work.
