## Summary

v1.12 turns config templates and configs into Kubernetes resources reconciled by the controller,
and adds a set of composition features behind feature gates: SourceDefinition and CEL property
expressions, `forEach` workflow steps, module and addon components, and definition inheritance.
vela-core now manages its own admission webhook and cluster-gateway serving certificates.

## Breaking changes

- **Trait conflicts.** Admission rejects an Application whose traits conflict through
  `TraitDefinition.spec.conflictsWith`; existing ones are denied on their next update. See
  [Trait conflicts](/upgrade-guides/v1.12/#trait-conflicts)
  ([#7303](https://github.com/kubevela/kubevela/pull/7303), backported to v1.11.1).
- **Config templates and configs.** They are now `ConfigTemplate` and `Config` resources: users need
  permissions on them, `outputs` objects go to the Config's namespace, and the controller publishes
  to Nacos. See [Config templates and configs](/upgrade-guides/v1.12/#config-templates-and-configs).
- **Workflow HTTP guard.** Workflow `request`, `webhook` and HTTP steps refuse metadata and
  link-local addresses, and read deny lists from labelled ConfigMaps
  ([GHSA-8p2m-f3vg-8jwg](https://github.com/kubevela/kubevela/security/advisories/GHSA-8p2m-f3vg-8jwg),
  backported to v1.11.1).

## Behaviour changes

- **Runtime certificates.** vela-core creates, reuses and renews the admission webhook and
  cluster-gateway serving certificates and sets their `caBundle`, instead of the
  `kube-webhook-certgen` Jobs. Argo CD users need `ignoreDifferences` for the webhook
  `failurePolicy`; see [Runtime certificates](/upgrade-guides/v1.12/#runtime-certificates)
  ([#7477](https://github.com/kubevela/kubevela/pull/7477), backported to v1.11.1).
- The `RestrictDefinitionNamespaces` feature gate is on by default. It enforces a definition's
  `spec.restrictions`, or its `definition.oam.dev/restrict-namespaces` annotation, when an
  Application is written, and does nothing until a definition declares a restriction.

## CRD changes

- New CRDs `configs.config.oam.dev` (`Config`), `configtemplates.config.oam.dev`
  (`ConfigTemplate`) and `sourcedefinitions.core.oam.dev` (`SourceDefinition`).
- `componentdefinitions`, `definitionrevisions`, `policydefinitions`, `traitdefinitions` and
  `workflowstepdefinitions` add definition restrictions and inheritance (`spec.extends`).
- `applications` and `applicationrevisions` add Application `sources`.
- `workflows` (and the Application workflow) add `forEach` steps.

Apply the CRDs before `helm upgrade`; see the
[upgrade guide](/upgrade-guides/v1.12/#config-templates-and-configs) for the commands.

## CLI changes

- `vela config-template migrate` and `vela config migrate` adopt v1.11 templates and configs; see
  [Migrate Configs to ConfigTemplate and Config](/upgrade-guides/v1.12/config-migration/).
- `vela def test` runs CUE tests for X-Definitions.
- `vela module` (`init`, `deploy`, `publish`, `registry`) manages modules.
- `vela mcp` serves KubeVela to AI agents over the Model Context Protocol.
- `vela config create` and `vela config-template apply` now create `Config` and `ConfigTemplate`
  resources.

Each command's flags are on its page under [vela CLI](/docs/next/cli/vela/).

## New features

- **Config templates and configs as resources**: `ConfigTemplate` and `Config`, with template scope,
  cross-namespace access, sensitive rules and Nacos publishing from the controller; see
  [Config Template](/docs/next/reference/config-template/).
- **SourceDefinition** and CEL `$( )` property expressions, including reading another component's
  output (`EnableCelExpressions`).
- **Workflow**: `forEach` steps with items from expressions and named by a key, CEL conditions on
  steps, expressions resolved when each step runs, and restarting before the first run.
- **Modules**: install a module as an Application component or inline with an addon, with
  identity stamping and hub and runtime placement (`EnableModuleComponent`).
- **Declarative addon component** (`EnableAddonComponent`).
- **Definitions**: inheritance and abstract definitions (`EnableDefinitionInheritance`), namespace
  restrictions, per-namespace usage quotas, and admission validation of WorkflowStepDefinition
  templates.
- **defkit**: Application-scoped and global policies, definition inheritance, reading a `forEach`
  pass from a step template, and expression-based validator messages.
- **Workflow steps**: configurable HTTP timeout on `request`, `webhook` and `notification`.
- **Traits**: `sidecar` supports `ports` (backported to v1.11.1).

## Bug fixes

- Built-in definitions: fixes across components, traits and workflow steps so every documented
  parameter renders ([#7445](https://github.com/kubevela/kubevela/pull/7445)). A changed Pod
  template restarts Pods, so test affected Applications before upgrading. Parameters are in the
  [Reference](/docs/next/end-user/components/references/) pages.
- `helmchart` releases install on the topology's clusters as the Application's user.
- Resource keeper honours shared-resource, GC-propagation and orphan-finalizer protections on
  delete (backported to v1.11.1).
- PolicyDefinitions are validated with the compiler of their scope, and global and
  Application-scoped policy changes propagate (backported to v1.11.1).
